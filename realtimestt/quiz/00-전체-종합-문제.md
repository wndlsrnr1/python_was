# 전체 종합 문제

## 객관식 문제

### 1. 실시간 STT 시스템의 전체 데이터 흐름 순서는?

① WebSocket → 오디오 변환 → 오디오 저장 → gRPC → 결과 처리  
② WebSocket → 오디오 저장 → 오디오 변환 → gRPC → 결과 처리  
③ WebSocket → 오디오 저장 → gRPC → 오디오 변환 → 결과 처리  
④ WebSocket → gRPC → 오디오 변환 → 오디오 저장 → 결과 처리  

**정답**: ②  
**해설**: 전체 데이터 흐름은 WebSocket으로 오디오 청크 수신 → AudioPipeline으로 저장 → AudioAdapter로 형식 변환(WebM → LINEAR16 PCM) → gRPC로 STT 서버 통신 → STTHandler로 결과 처리 및 전송 순서입니다.

---

### 2. SessionContext가 생성되는 시점은?

① WebSocket 연결 수립 시  
② start 메시지 수신 시  
③ 첫 오디오 청크 수신 시  
④ end 메시지 수신 시  

**정답**: ②  
**해설**: SessionContext는 `start` 메시지를 받았을 때 세션 검증, 저장 경로 생성, 메타데이터 초기화 등을 수행한 후 생성됩니다.

---

### 3. gRPC 재연결 시나리오에서 수행해야 할 작업이 아닌 것은?

① 기존 Queue 종료  
② 기존 Queue 재사용  
③ 새 Queue 생성  
④ ffmpeg 프로세스 재시작  

**정답**: ②  
**해설**: asyncio.Queue는 한 번 종료되면 재사용할 수 없으므로, 재시작 시 기존 Queue를 재사용하지 않고 새로운 Queue를 생성해야 합니다.

---

### 4. 전체 시스템에서 오디오 형식 변환이 필요한 이유는?

① STT 서버가 WebM 형식을 요구하기 때문  
② 브라우저가 LINEAR16 PCM을 지원하지 않기 때문  
③ STT 서버가 LINEAR16 PCM 형식을 요구하기 때문  
④ 변환이 필요하지 않다  

**정답**: ③  
**해설**: 웹 브라우저에서 녹음된 WebM 오디오를 STT 서버가 요구하는 LINEAR16 PCM 형식으로 변환해야 합니다.

---

### 5. 초기화 순서가 올바른 것은?

① Handler 초기화 → SessionContext 생성 → Queue 생성 → STT 태스크 시작  
② SessionContext 생성 → Handler 초기화 → Queue 생성 → STT 태스크 시작  
③ Handler 초기화 → Queue 생성 → SessionContext 생성 → STT 태스크 시작  
④ Queue 생성 → Handler 초기화 → SessionContext 생성 → STT 태스크 시작  

**정답**: ①  
**해설**: 초기화 순서는 WebSocket 연결 수립 → Handler 초기화 → start 메시지 수신 → SessionContext 생성 → Queue 생성 → STT 태스크 시작입니다.

---

### 6. 전체 시스템에서 비동기 처리가 필요한 이유는?

① 동기 처리가 불가능하기 때문  
② 여러 작업을 동시에 처리하여 성능을 최적화하기 때문  
③ 코드가 간단해지기 때문  
④ 메모리 사용량이 적기 때문  

**정답**: ②  
**해설**: 비동기 처리는 여러 작업(I/O 대기)을 동시에 처리하여 성능을 최적화합니다. 오디오 수신, 변환, STT 처리 등을 동시에 수행할 수 있습니다.

---

### 7. 재시작 시나리오에서 SessionContext에서 추출해야 하는 정보가 아닌 것은?

① input_format  
② language_code  
③ session_id  
④ api_token  

**정답**: ④  
**해설**: api_token은 SessionContext에 저장되지 않으며, STT 설정에서 조회합니다. input_format, language_code, session_id는 SessionContext에서 추출하여 재시작에 사용합니다.

---

## 빈칸 채우기

### 8. 전체 아키텍처 파이프라인에서 오디오 형식 변환은 (    )에서 (    )로 변환합니다.

**정답**: WebM, LINEAR16 PCM  
**해설**: AudioAdapter에서 WebM 형식의 오디오를 STT 서버가 요구하는 LINEAR16 PCM 형식으로 변환합니다.

---

### 9. 전체 시스템 통합 흐름에서 STT 처리 태스크는 (    ) 메시지를 받았을 때 시작됩니다.

**정답**: start  
**해설**: `start` 메시지를 받으면 세션을 초기화하고 SessionContext를 생성한 후, STT 처리 태스크를 시작합니다.

---

### 10. 재시작 시나리오에서 기존 Queue는 (    ) 신호를 보내 종료하고, 새로운 Queue를 생성해야 합니다.

**정답**: None  
**해설**: Queue에 `None`을 넣어 종료 신호를 보내면 제너레이터가 종료되고, 재시작 시 새로운 Queue를 생성해야 합니다.

---

### 11. 전체 시스템에서 Handler 패턴을 사용하면 각 Handler가 하나의 (    )만 가지므로 테스트가 용이합니다.

**정답**: 책임  
**해설**: Handler 패턴은 단일 책임 원칙을 준수하여 각 Handler가 하나의 책임만 가지므로, 각 Handler를 독립적으로 테스트할 수 있습니다.

---

### 12. SessionContext 패턴은 (    ) 객체를 사용하여 상태 동기화 문제를 해결합니다.

**정답**: 불변  
**해설**: SessionContext는 불변(immutable) 객체로 설계되어 있어, 상태를 변경할 때는 항상 새로운 객체를 생성합니다. 이를 통해 상태 동기화 문제를 해결합니다.

---

## O/X 문제

### 13. 전체 시스템에서 오디오 청크는 수신 즉시 파일에 저장되고, 동시에 STT 처리를 위해 Queue에 추가된다.

**정답**: O  
**해설**: 오디오 청크는 수신 즉시 AudioPipeline을 통해 파일에 저장되고, 동시에 STT 처리를 위해 Queue에 추가됩니다.

---

### 14. 재시작 시나리오에서 기존 ffmpeg 프로세스를 재사용할 수 있다.

**정답**: X  
**해설**: 재시작 시 새로운 stdout 파이프를 위해 ffmpeg 프로세스를 재시작해야 합니다. SessionContext에서 input_format 정보를 추출하여 새 프로세스를 시작합니다.

---

### 15. 전체 시스템에서 에러가 발생하면 모든 처리를 중단한다.

**정답**: X  
**해설**: 에러 처리 전략에 따라 다릅니다. WebSocket 전송 실패는 로깅만 하고 계속 진행하지만, STT 스트림 처리 중 예외 발생 시 에러를 전송하고 종료할 수 있습니다.

---

### 16. SessionContext는 연결 종료 시까지 유지되며, 재시작 시에도 정보를 보존한다.

**정답**: O  
**해설**: SessionContext는 연결 종료 시까지 유지되며, 재시작 시에도 정보를 보존하여 재시작에 필요한 모든 정보를 제공합니다.

## 서술형 문제

### 17. 전체 시스템의 데이터 흐름을 단계별로 설명하세요.

**정답**:  
전체 시스템의 데이터 흐름은 다음과 같습니다:
1. **WebSocket 연결**: 클라이언트가 WebSocket으로 연결하고 JWT 인증을 수행합니다.
2. **오디오 청크 수신**: WebSocket Consumer가 오디오 청크를 수신합니다.
3. **오디오 저장**: AudioPipeline을 통해 오디오 청크를 파일에 저장합니다.
4. **Queue 추가**: 오디오 청크를 asyncio.Queue에 추가합니다.
5. **오디오 변환**: AudioAdapter가 WebM을 LINEAR16 PCM으로 변환합니다.
6. **gRPC 통신**: gRPC Client가 STT 서버로 변환된 오디오를 전송합니다.
7. **결과 처리**: STTHandler가 STT 결과를 처리하고 WebSocket으로 전송합니다.

**해설**: 전체 시스템은 여러 단계를 거쳐 오디오를 수신, 저장, 변환, 처리하여 실시간으로 텍스트로 변환합니다.

---

### 18. 재시작 시나리오의 전체 과정을 설명하세요.

**정답**:  
재시작 시나리오의 전체 과정은 다음과 같습니다:
1. **기존 STT 태스크 종료**: 실행 중인 STT 처리 태스크를 취소합니다.
2. **기존 Queue 종료**: `close_queue()`를 통해 `None` 종료 신호를 전송합니다.
3. **새 Queue 생성**: asyncio.Queue는 재사용할 수 없으므로 새로운 Queue를 생성합니다.
4. **SessionContext에서 정보 추출**: input_format, language_code, interim_results, session_id 등을 추출합니다.
5. **ffmpeg 프로세스 재시작**: SessionContext의 input_format을 사용하여 새 프로세스를 시작합니다.
6. **새 STT 태스크 시작**: 새 Queue와 새 ffmpeg 프로세스로 STT 처리 태스크를 시작합니다.

**해설**: 재시작 시 모든 리소스를 정리하고 새로 생성하여 정상 동작을 재개합니다.

---

### 19. SessionContext 패턴이 전체 시스템에서 중요한 이유를 설명하세요.

**정답**:  
SessionContext 패턴이 중요한 이유는 다음과 같습니다:
1. **상태 동기화 보장**: 불변 객체를 사용하여 여러 태스크가 동시에 실행되어도 상태 동기화 문제를 방지합니다.
2. **재시작 시나리오 지원**: 재시작 시 필요한 모든 정보(input_format, language_code 등)를 SessionContext에서 추출할 수 있습니다.
3. **예측 가능성**: 상태 변경이 항상 새 객체 생성으로 표현되어 어떤 상태 변경이 발생했는지 명확히 추적할 수 있습니다.
4. **디버깅 용이**: 각 상태 변경 시점의 컨텍스트를 보존하여 디버깅이 용이합니다.

**해설**: SessionContext 패턴은 전체 시스템의 상태 관리를 안전하고 예측 가능하게 만듭니다.

---

### 20. 전체 시스템에서 Handler 패턴이 어떻게 활용되는지 설명하세요.

**정답**:  
Handler 패턴은 다음과 같이 활용됩니다:
1. **MessageHandler**: WebSocket 메시지 처리(start, end, audio), SessionContext 생성/업데이트, 오디오 큐 관리
2. **ResponseHandler**: 응답 전송(ack, error), Consumer에 직접 의존하지 않고 send_func를 파라미터로 받음
3. **STTHandler**: STT 스트림 처리 및 결과 전송, AudioHandler.generate_chunks() 사용
4. **AudioHandler**: 오디오 청크 제너레이터, Queue에서 청크를 비동기적으로 생성

각 Handler는 명확한 책임을 가지며, 느슨한 결합을 유지하여 테스트와 재사용이 용이합니다.

**해설**: Handler 패턴은 전체 시스템의 책임을 분리하여 코드 구조를 개선하고 유지보수성을 향상시킵니다.

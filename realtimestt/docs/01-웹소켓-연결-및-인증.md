## WebSocket 프로토콜 기초

### HTTP vs WebSocket

HTTP는 요청-응답 모델을 따르는 단방향 통신 프로토콜입니다. 클라이언트가 요청을 보내면 서버가 응답을 반환하고 연결이 종료됩니다. 반면 WebSocket은 양방향 통신을 지원하는 프로토콜로, 한 번 연결을 수립하면 지속적으로 데이터를 주고받을 수 있습니다.

**HTTP의 한계:**

- 클라이언트가 항상 요청을 먼저 보내야 함
- 실시간 데이터 전송에 비효율적
- 서버에서 클라이언트로의 즉각적인 데이터 전송 불가

**WebSocket의 장점:**

- 양방향 실시간 통신
- 낮은 오버헤드 (HTTP 헤더 없음)
- 서버에서 클라이언트로의 푸시 가능

### WebSocket 연결 수립 과정

WebSocket 연결은 HTTP 업그레이드 요청으로 시작됩니다:

```
1. 클라이언트: HTTP Upgrade 요청
   GET /ws/realtime-stt/ HTTP/1.1
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
   Sec-WebSocket-Version: 13

2. 서버: 101 Switching Protocols 응답
   HTTP/1.1 101 Switching Protocols
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

연결이 수립되면 양방향으로 데이터를 주고받을 수 있습니다.

## Django Channels 구조

Django Channels는 Django에 비동기 및 WebSocket 지원을 추가하는 확장입니다.

### ASGI (Asynchronous Server Gateway Interface)

Channels는 ASGI를 사용하여 비동기 요청을 처리합니다. ASGI는 WSGI의 비동기 버전으로, WebSocket과 같은 장기 연결을 지원합니다.

**ASGI 애플리케이션 구조:**

```python
async def application(scope, receive, send):
    if scope["type"] == "http":
        # HTTP 요청 처리
    elif scope["type"] == "websocket":
        # WebSocket 연결 처리
```

### scope 객체 이해

`scope`는 ASGI 프로토콜의 핵심 구성 요소로, 연결에 대한 모든 정보를 담은 딕셔너리입니다. 연결 수립 시 한 번 생성되어 연결 종료까지 유지되며, ASGI 애플리케이션과 미들웨어에서 공유됩니다.

#### scope 객체의 역할

`scope`는 다음과 같은 역할을 합니다:

1. **연결 정보 제공**: 연결 타입, 경로, 클라이언트 정보 등
2. **요청 메타데이터 저장**: HTTP 헤더, 쿠키, 쿼리 파라미터 등
3. **컨텍스트 공유**: 미들웨어와 애플리케이션 간 데이터 전달
4. **인증 정보 저장**: 인증된 사용자 정보 저장

#### scope의 주요 필드

`scope`는 연결 타입에 따라 다른 필드를 포함하지만, 공통 필드는 다음과 같습니다:

**공통 필드:**

- `type`: 연결 타입 (`"http"`, `"websocket"`, `"lifespan"`)
- `path`: 요청 경로 (예: `"/ws/realtime-stt/"`)
- `headers`: HTTP 헤더 리스트 (바이트 튜플 형식)
  ```python
  [(b"host", b"localhost:8000"), (b"cookie", b"access_token=...")]
  ```
- `client`: 클라이언트 주소 튜플 `(ip, port)`
  ```python
  ("127.0.0.1", 54321)
  ```
- `server`: 서버 주소 튜플 `(ip, port)`
  ```python
  ("127.0.0.1", 8000)
  ```

**WebSocket 전용 필드:**

- `subprotocols`: 서브프로토콜 리스트 (선택적)
- `query_string`: 쿼리 문자열 (바이트 형식)

**미들웨어에서 추가되는 필드:**

- `user`: 인증된 사용자 객체 (미들웨어에서 설정)

#### WebSocket scope의 특수성

WebSocket 연결 시 `scope`는 다음과 같은 특성을 가집니다:

1. **연결 타입**: `scope["type"]`이 `"websocket"`으로 설정됨
2. **초기 헤더 보존**: HTTP Upgrade 요청의 헤더가 `scope["headers"]`에 포함됨
3. **쿠키 접근**: 인증에 필요한 쿠키는 초기 헤더에서만 추출 가능
4. **사용자 정보**: 미들웨어에서 `scope["user"]`에 사용자 정보 설정 가능

**WebSocket scope 예시:**

```python
{
    "type": "websocket",
    "path": "/ws/realtime-stt/",
    "headers": [
        (b"host", b"localhost:8000"),
        (b"cookie", b"access_token=eyJ...; refresh_token=eyJ..."),
        (b"upgrade", b"websocket"),
        (b"connection", b"Upgrade"),
    ],
    "client": ("127.0.0.1", 54321),
    "server": ("127.0.0.1", 8000),
    "subprotocols": [],
    "query_string": b"",
    "user": <User: username>,  # 미들웨어에서 설정됨
}
```

#### scope 객체의 생명주기

`scope` 객체는 다음과 같은 생명주기를 가집니다:

1. **생성**: ASGI 서버가 연결 요청을 받을 때 생성
2. **미들웨어 처리**: 미들웨어 체인을 거치며 정보 추가/수정
3. **Consumer 전달**: Django Channels가 Consumer에 `self.scope`로 제공
4. **연결 종료**: 연결이 종료되면 scope도 함께 소멸

**중요 사항:**

- `scope`는 연결당 하나만 존재하며, 연결 종료까지 유지됨
- `scope`는 딕셔너리이므로 필드를 추가하거나 수정할 수 있음
- 미들웨어에서 `scope["user"]`를 설정하면 Consumer에서 `self.scope.get("user")`로 접근 가능
- `scope`는 읽기 전용이 아니므로, 필요시 필드를 추가하거나 수정할 수 있음

#### scope vs self.scope

Django Channels의 Consumer에서는 `self.scope`로 접근합니다:

```python
class RealtimeSTTConsumer(AsyncWebsocketConsumer):
    async def connect(self):
        # self.scope는 ASGI scope 객체
        scope = self.scope
        
        # scope에서 정보 추출
        client_host = scope.get("client", [None, None])[0]
        user = scope.get("user")
```

**차이점:**

- **ASGI 애플리케이션**: `scope`를 직접 파라미터로 받음
- **Django Channels Consumer**: `self.scope`로 접근
- **내용**: 동일한 딕셔너리 객체

### Consumer 패턴

Channels는 Consumer 패턴을 사용하여 WebSocket 연결을 처리합니다. Consumer는 WebSocket 이벤트를 처리하는 클래스입니다.

**주요 이벤트:**

- `connect`: 연결 수립 시 호출
- `disconnect`: 연결 종료 시 호출
- `receive`: 메시지 수신 시 호출

## JWT 쿠키 인증 원리

### JWT (JSON Web Token) 구조

JWT는 세 부분으로 구성됩니다:

1. **Header**: 토큰 타입과 알고리즘
2. **Payload**: 사용자 정보 및 클레임
3. **Signature**: 서명 (위조 방지)

**JWT 예시:**

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoxMjN9.signature
```

[WebSocket 인증(정정)]

WebSocket 인증은 “연결 직전의 HTTP Upgrade(초기 핸드셰이크)” 단계에서만 처리할 수 있습니다.
이때 요청 헤더에 Cookie/Authorization 같은 값이 실려 오며, 서버는 이 초기 요청에서 토큰을 검증해 인증을 완료합니다.

핵심:

- 초기 연결(HTTP Upgrade) 때만 헤더/쿠키가 전달됨
- 연결이 성립된 이후(WebSocket 프레임 통신)는 헤더가 없어서 “추가 헤더 기반 인증”이 불가
- 브라우저 WebSocket API는 사용자 정의 헤더(예: Authorization) 설정이 제한적이라,
  실무에서는 브라우저가 자동 포함하는 쿠키(또는 쿼리스트링/서브프로토콜 등)로 토큰을 전달하는 방식이 흔함

## 인증 미들웨어 구현

### JWTWebSocketAuthMiddleware

`transcription/middleware/websocket_jwt_auth.py`에 구현된 인증 미들웨어는 다음과 같이 동작합니다:

```python
class JWTWebSocketAuthMiddleware:
    def __init__(self, inner):
        self.inner = inner
        self.jwt_auth = JWTAuthentication()

    async def __call__(self, scope, receive, send):
        if scope["type"] == "websocket":
            # 쿠키 추출
            cookies = self._extract_cookies(scope)

            # JWT 토큰 검증 및 사용자 인증
            user = await self._authenticate_from_cookies(cookies, scope)

            # scope에 사용자 설정
            scope["user"] = user

        return await self.inner(scope, receive, send)
```

### 쿠키 추출

WebSocket scope의 headers에서 쿠키를 추출합니다:

```python
def _extract_cookies(self, scope):
    cookies = {}
    headers = scope.get("headers", [])

    for header_name, header_value in headers:
        if header_name.lower() == b"cookie":
            cookie_header = header_value.decode("utf-8")
            # "name1=value1; name2=value2" 형식 파싱
            for part in cookie_header.split(";"):
                if "=" in part:
                    name, value = part.split("=", 1)
                    cookies[name.strip()] = value.strip()
            break

    return cookies
```

### 토큰 검증 및 사용자 인증

1. **Access 토큰 검증**: access_token 쿠키가 있으면 먼저 검증
2. **Refresh 토큰 갱신**: access 토큰이 없거나 만료된 경우 refresh_token으로 새 access 토큰 발급
3. **사용자 조회**: 검증된 토큰으로 사용자 정보 조회

```python
async def _authenticate_from_cookies(self, cookies, scope):
    # 1. access 토큰 검증 시도
    raw_access = cookies.get("access_token")
    if raw_access:
        try:
            validated_token = await sync_to_async(
                self.jwt_auth.get_validated_token
            )(raw_access)
            if validated_token:
                user = await sync_to_async(self.jwt_auth.get_user)(validated_token)
                return user
        except (InvalidToken, TokenError):
            pass

    # 2. refresh 토큰으로 새 access 토큰 발급
    raw_refresh = cookies.get("refresh_token")
    if raw_refresh:
        new_tokens = await sync_to_async(
            TokenService.issue_access_from_refresh
        )(raw_refresh)
        # 새 access 토큰으로 사용자 인증
        # ...

    return AnonymousUser()
```

## Consumer 연결 수립 과정

### RealtimeSTTConsumer 구조

`transcription/consumers/realtime_stt_consumer.py`의 Consumer는 Handler 패턴을 사용하여 책임을 분리합니다:

```python
class RealtimeSTTConsumer(AsyncWebsocketConsumer):
    """실시간 STT WebSocket Consumer

    오디오 데이터를 실시간으로 수신하고 파일 시스템에 저장합니다.
    """
    
    async def connect(self) -> None:
        """WebSocket 연결 수립"""
        await self.accept()
        
        # 세션 컨텍스트 초기화
        self.session_context: SessionContext | None = None
        self.stt_processing_task: asyncio.Task[None] | None = None
        
        # Handler 초기화
        self.message_handler = MessageHandler(self)
        self.response_handler = ResponseHandler()
        self.stt_handler = STTHandler()

    async def disconnect(self, close_code: int) -> None:
        """WebSocket 연결 종료"""
        # STT 처리 태스크 종료
        if self.stt_processing_task:
            self.stt_processing_task.cancel()
        
        # 오디오 큐 종료
        await self.message_handler.close_queue()
        
        # 최종 메타데이터 저장
        if self.session_context:
            # SessionContext에서 정보 추출하여 저장
            # ...

    async def receive(self, text_data=None, bytes_data=None):
        """메시지 수신 처리"""
        if text_data:
            # MessageHandler로 위임
            result = await self.message_handler.handle_text(...)
            if result is not None:
                self.session_context = result
        elif bytes_data:
            # MessageHandler로 위임
            if self.session_context:
                self.session_context = await self.message_handler.handle_audio(...)
```

### Handler 패턴

Consumer는 각 책임을 Handler 클래스로 분리합니다:

- **MessageHandler**: WebSocket 메시지 처리 (start, end, audio)
- **ResponseHandler**: 응답 전송 (ack, error)
- **STTHandler**: STT 스트림 처리
- **AudioHandler**: 오디오 청크 생성

이 패턴의 장점:
- **단일 책임 원칙**: 각 Handler가 하나의 책임만 가짐
- **테스트 용이성**: 각 Handler를 독립적으로 테스트 가능
- **재사용성**: Handler를 다른 Consumer에서도 사용 가능
- **유지보수성**: 변경 사항이 해당 Handler에만 영향

### 연결 수립 처리

`connect` 메서드에서 다음을 수행합니다:

1. **연결 수락**: `await self.accept()`로 WebSocket 연결 수립
2. **Handler 초기화**: MessageHandler, ResponseHandler, STTHandler 생성
3. **세션 컨텍스트 초기화**: SessionContext를 None으로 초기화 (start 메시지에서 생성)

```python
async def connect(self) -> None:
    """WebSocket 연결 수립"""
    scope = self.scope
    client_host = (
        scope.get("client", [None, None])[0] if scope.get("client") else "unknown"
    )

    logger.info(f"WebSocket 연결 시도: client={client_host}")

    try:
        await self.accept()

        # 세션 컨텍스트 초기화 (start 메시지에서 생성됨)
        self.session_context: SessionContext | None = None
        self.stt_processing_task: asyncio.Task[None] | None = None

        # Handler 초기화
        self.message_handler = MessageHandler(self)
        self.response_handler = ResponseHandler()
        self.stt_handler = STTHandler()

        # 사용자 정보 확인
        user = scope.get("user")
        if user and user.is_authenticated:
            logger.info(f"WebSocket 연결 수립 성공: user_id={user.id}")
        else:
            logger.warning(f"WebSocket 연결 수립 (인증 없음): client={client_host}")

    except Exception as e:
        logger.error(
            f"WebSocket 연결 수립 실패: client={client_host}, error={str(e)}",
            exc_info=True,
        )
        raise
```

### Handler 초기화

각 Handler는 Consumer 초기화 시 생성됩니다:

```python
# Handler 초기화
self.message_handler = MessageHandler(self)  # Consumer 참조 필요
self.response_handler = ResponseHandler()  # 독립적
self.stt_handler = STTHandler()  # 독립적
```

Handler 간 의존성:
- **MessageHandler**: Consumer 참조 필요 (scope 접근)
- **ResponseHandler**: 독립적 (send_func를 파라미터로 받음)
- **STTHandler**: 독립적 (send_func를 파라미터로 받음)

### 연결 종료 처리

`disconnect` 메서드에서 다음을 수행합니다:

1. **STT 처리 태스크 종료**: 실행 중인 STT 처리 태스크 취소
2. **오디오 큐 정리**: MessageHandler를 통해 종료 신호 전송
3. **메타데이터 저장**: SessionContext에서 정보를 추출하여 최종 메타데이터 저장

```python
async def disconnect(self, close_code: int) -> None:
    """WebSocket 연결 종료"""
    session_id = self.session_context.session_id if self.session_context else None
    chunk_count = self.session_context.chunk_count if self.session_context else 0

    logger.info(
        f"WebSocket 연결 종료 시작: session_id={session_id}, "
        f"close_code={close_code}, chunks={chunk_count}"
    )

    try:
        # 1. STT 처리 태스크 종료
        if self.stt_processing_task and not self.stt_processing_task.done():
            self.stt_processing_task.cancel()
            try:
                await self.stt_processing_task
            except asyncio.CancelledError:
                logger.info("STT 처리 태스크 취소됨")

        # 2. 오디오 큐 종료 (MessageHandler를 통해)
        await self.message_handler.close_queue()

        # 3. 최종 메타데이터 저장 (SessionContext에서 정보 추출)
        if self.session_context:
            updated_metadata = self.session_context.metadata.copy()
            updated_metadata["total_chunks"] = self.session_context.chunk_count
            updated_metadata["end_time"] = timezone.now().isoformat()
            updated_metadata["duration_seconds"] = (
                timezone.now() - self.session_context.start_time
            ).total_seconds()

            await sync_to_async(RealtimeSTTService.MetadataPipeline.save_json)(
                self.session_context.base_path, updated_metadata
            )

            logger.info(
                f"최종 메타데이터 저장 완료: session_id={session_id}, "
                f"path={self.session_context.base_path}"
            )

    except Exception as e:
        logger.error(
            f"연결 종료 중 오류: session_id={session_id}, "
            f"close_code={close_code}, error={str(e)}",
            exc_info=True,
        )
```

### Handler를 통한 리소스 정리

리소스 정리는 각 Handler의 책임으로 분리됩니다:

```python
# MessageHandler의 책임
await self.message_handler.close_queue()  # 오디오 큐 종료

# SessionContext에서 정보 추출
if self.session_context:
    # SessionContext의 불변성 덕분에 안전하게 정보 추출 가능
    chunk_count = self.session_context.chunk_count
    base_path = self.session_context.base_path
```

## 부록: Python async vs JavaScript/Java 비교

### 핵심 개념

세 언어 모두 비동기로 I/O 대기 중 다른 작업을 처리합니다. 구현 방식은 다릅니다.

### 문법 비교

#### JavaScript (Promise 기반)

```javascript
// 비동기로 요청을 보내고 받는 과정
async function fetchData() {
  const response = await fetch("/api/data");
  const data = await response.json();
  return data;
}
```

#### Java (CompletableFuture)

```java
// CompletableFuture 체이닝
CompletableFuture<String> fetchData() {
    return CompletableFuture
        .supplyAsync(() -> fetch("/api/data"))
        .thenApply(response -> parseJson(response));
}
```

#### Python (async/await)

```python
async def fetch_data():
    response = await fetch('/api/data')
    data = await response.json()
    return data
```

**비교**: Python과 JavaScript는 문법이 거의 동일합니다. Java는 체이닝 방식입니다.

### 실행 모델 차이

#### JavaScript

- 단일 스레드 이벤트 루프
- 비동기 작업은 백그라운드에서 처리 후 콜백 큐로 복귀
- 병렬 처리: Web Workers 사용

#### Java

- 멀티 스레드 기반
- CompletableFuture는 스레드 풀에서 실행
- 실제 병렬 처리 가능

#### Python

- 단일 스레드 이벤트 루프 (asyncio)
- 코루틴이 협력적으로 실행
- I/O 대기 중에만 다른 코루틴 실행

### 실제 사용 예시

현재 코드 기준:

```python
# Python - 현재 코드 패턴
async def connect(self):
    await self.accept()  # I/O 대기 중 다른 작업 처리 가능
    # ... 초기화 로직
```

```javascript
// JavaScript - 동일한 패턴
async function connect() {
  await this.accept(); // 동일한 문법
  // ... 초기화 로직
}
```

```java
// Java - 다른 패턴
public CompletableFuture<Void> connect() {
    return accept()
        .thenRun(() -> {
            // ... 초기화 로직
        });
}
```

### Python async의 특징

- **장점**: JavaScript와 유사한 문법, I/O 대기 시 효율적
- **단점**: CPU 집약 작업에는 부적합 (GIL 제약)
- **적합한 경우**: WebSocket, HTTP 요청, DB 쿼리 등 I/O 대기 작업

현재 웹소켓 코드처럼 I/O 대기 시간이 긴 경우에 적합합니다.

## 부록: Python 비동기 실행 환경과 제약사항

### 이벤트 루프 필요성

Python 비동기는 **이벤트 루프(Event Loop)** 위에서만 동작합니다. 이벤트 루프가 없으면 실행할 수 없습니다.

```python
# ❌ 이벤트 루프 없이 실행 불가
async def my_function():
    await some_async_operation()

my_function()  # RuntimeError 발생!

# ✅ 이벤트 루프에서 실행
import asyncio

async def my_function():
    await some_async_operation()

asyncio.run(my_function())  # 이벤트 루프 생성 및 실행
```

#### 이벤트 루프 동작 원리

이벤트 루프는 비동기 작업을 관리하는 핵심 메커니즘입니다:

1. **코루틴 스케줄링**: `await`로 일시 중단된 코루틴을 큐에 등록
2. **I/O 대기**: 네트워크, 파일 등의 I/O 작업이 완료될 때까지 대기
3. **작업 전환**: I/O 대기 중 다른 코루틴 실행 (협력적 멀티태스킹)
4. **결과 반환**: I/O 완료 시 해당 코루틴 재개

```python
import asyncio

async def task1():
    print("작업 1 시작")
    await asyncio.sleep(1)  # I/O 대기 → 이벤트 루프가 다른 작업 실행
    print("작업 1 완료")

async def task2():
    print("작업 2 시작")
    await asyncio.sleep(1)  # I/O 대기 → 이벤트 루프가 다른 작업 실행
    print("작업 2 완료")

# 이벤트 루프가 두 작업을 동시에 관리
async def main():
    await asyncio.gather(task1(), task2())  # 병렬 실행

asyncio.run(main())
# 출력:
# 작업 1 시작
# 작업 2 시작
# (1초 대기)
# 작업 1 완료
# 작업 2 완료
```

**핵심**: 이벤트 루프는 단일 스레드에서 여러 비동기 작업을 효율적으로 관리합니다.

### 실행 환경 종류

#### ASGI 서버 (Django Channels, FastAPI 등)

ASGI 서버가 이벤트 루프를 자동으로 제공합니다:

```python
# Django Channels - ASGI 서버가 이벤트 루프 제공
class RealtimeSTTConsumer(AsyncWebsocketConsumer):
    async def connect(self):  # 이미 이벤트 루프 안에서 실행됨
        await self.accept()
```

#### 독립 스크립트

직접 이벤트 루프를 생성해야 합니다:

```python
import asyncio

async def main():
    # 비동기 작업
    pass

if __name__ == "__main__":
    asyncio.run(main())  # 이벤트 루프 생성 및 실행
```

### 동기 환경에서 사용 불가

동기 함수에서 `async` 함수를 직접 호출할 수 없습니다:

```python
# ❌ 불가능
def sync_function():
    result = async_function()  # 에러!

# ✅ 해결 방법: asyncio.run() 사용
import asyncio

def sync_function():
    result = asyncio.run(async_function())
```

**주의**: 이미 실행 중인 이벤트 루프가 있으면 `asyncio.run()`을 사용할 수 없습니다.

### 기본 제약사항

#### 1. GIL (Global Interpreter Lock) 제약

- 단일 스레드에서 실행
- CPU 집약 작업에는 비효율적
- I/O 대기 작업에 적합

```python
# ❌ CPU 집약 작업 - 비효율적
async def cpu_intensive():
    result = sum(i**2 for i in range(10000000))  # 비동기 이점 없음

# ✅ I/O 대기 작업 - 효율적
async def io_intensive():
    response = await http_client.get('/api/data')  # I/O 대기 중 다른 작업 가능
```

#### 2. 동기 코드와 혼용 주의

동기 블로킹 코드를 비동기 함수에서 사용하면 이벤트 루프가 멈춥니다:

```python
# ❌ 나쁜 예: 동기 블로킹 코드
async def bad_example():
    time.sleep(1)  # 이벤트 루프 블로킹!

# ✅ 좋은 예: 비동기 대기
async def good_example():
    await asyncio.sleep(1)  # 이벤트 루프 블로킹 안 함
```

#### 3. 이벤트 루프 중첩 불가

이미 실행 중인 이벤트 루프에서 `asyncio.run()`을 호출하면 에러가 발생합니다:

```python
# ❌ 나쁜 예
async def inner():
    asyncio.run(another_async())  # RuntimeError!

# ✅ 좋은 예
async def inner():
    await another_async()  # 같은 이벤트 루프에서 실행
```

### 비동기/동기 함수 호출 관계

#### 비동기 → 동기 함수 호출: 가능

비동기 함수에서 동기 함수를 호출할 수 있습니다 (단, 블로킹됨):

```python
# ✅ 가능: 비동기에서 동기 함수 호출
async def connect(self):
    self.start_time = timezone.now()  # 동기 함수 호출 가능
    logger.info("연결됨")  # 동기 함수 호출 가능
    await self.accept()  # 비동기 함수 호출
```

#### 동기 → 비동기 함수 호출: 직접 불가능

동기 함수에서 `await`를 사용할 수 없습니다:

```python
# ❌ 불가능: 동기 함수에서 await 사용
def sync_function():
    result = await async_function()  # SyntaxError!

# ✅ 해결 방법: asyncio.run() 사용
import asyncio

def sync_function():
    result = asyncio.run(async_function())
```

#### sync_to_async: 동기 함수를 비동기로 변환

비동기 함수에서 동기 함수를 호출할 때, 직접 호출하면 이벤트 루프가 블로킹됩니다. `sync_to_async`를 사용하면 별도 스레드에서 실행하여 블로킹을 방지할 수 있습니다.

**역할**: Django의 `asgiref.sync` 모듈에서 제공하는 함수로, 동기 함수를 비동기 함수로 변환합니다.

**사용법**:

```python
from asgiref.sync import sync_to_async

# ❌ 직접 호출: 이벤트 루프 블로킹
async def handle_start(self, data):
    session = RealtimeSTTService.validate_session(session_id, user)  # 블로킹!

# ✅ sync_to_async 사용: 이벤트 루프 블로킹 방지
async def handle_start(self, data):
    session = await sync_to_async(RealtimeSTTService.validate_session)(session_id, user)
```

**실제 코드 예시**:

```python
# realtimestt/codes/app.py (82번 라인)
self.consumer.session = await sync_to_async(RealtimeSTTService.validate_session)(
    session_id, self.consumer.user
)
```

이 코드는:

- `RealtimeSTTService.validate_session`은 동기 함수
- `handle_start`는 비동기 함수 (`async def`)
- 비동기 함수에서 동기 함수를 호출하려면 `sync_to_async`로 변환 필요

**동작 원리**:

1. `sync_to_async`가 동기 함수를 래핑하여 비동기 함수로 변환
2. 별도 스레드에서 동기 함수 실행
3. 완료되면 이벤트 루프에 결과 반환
4. 이벤트 루프는 다른 코루틴을 계속 실행 가능 (블로킹 없음)

**요약**:

| 항목       | 내용                                    |
| ---------- | --------------------------------------- |
| **용도**   | 비동기 환경에서 동기 함수 호출          |
| **위치**   | `asgiref.sync` 모듈                     |
| **사용법** | `await sync_to_async(동기함수)(인자들)` |
| **효과**   | 이벤트 루프 블로킹 방지                 |

### WebSocket 실행 환경

**WebSocket은 이미 비동기 환경에서 시작됩니다.** Django Channels의 WebSocket Consumer는 ASGI 서버가 제공하는 이벤트 루프에서 실행됩니다.

```python
# Django Channels가 이미 이벤트 루프를 제공
class RealtimeSTTConsumer(AsyncWebsocketConsumer):
    # 이 함수는 이미 이벤트 루프 안에서 실행됨
    async def connect(self):
        # ✅ 비동기 함수 호출 가능
        await self.accept()

        # ✅ 동기 함수도 호출 가능 (단, 블로킹됨)
        self.start_time = timezone.now()

        # ✅ 다른 비동기 함수 호출 가능
        await self.initialize_session()
```

**실행 흐름:**

```
ASGI 서버 (Uvicorn/Daphne)
    └─→ 이벤트 루프 시작
        └─→ WebSocket 연결 요청 수신
            └─→ RealtimeSTTConsumer.connect() 호출
                └─→ 이미 비동기 환경이므로 await 사용 가능
```

### 요약

| 항목               | 내용                                              |
| ------------------ | ------------------------------------------------- |
| **실행 환경**      | 이벤트 루프(Event Loop) 필수                      |
| **동기 환경 사용** | 불가능 (이벤트 루프 필요)                         |
| **비동기 → 동기**  | ✅ 가능 (단, 블로킹됨)                            |
| **동기 → 비동기**  | ❌ 직접 불가 (`await` 사용 불가)                  |
| **제약사항**       | GIL 제약, CPU 집약 작업 부적합                    |
| **적합한 경우**    | I/O 대기 작업 (WebSocket, HTTP, DB 쿼리)          |
| **주의사항**       | 동기 블로킹 코드 혼용 금지, 이벤트 루프 중첩 불가 |

**핵심 개념:**

# 4장: 프로세스 모델 및 워커 이해

## 4.1 프로세스 구조

Gunicorn은 **마스터-워커 모델**을 사용합니다.

### 마스터 프로세스 (Master Process)

- **역할**: 워커 프로세스들을 관리
- **책임**:
  - 워커 프로세스 생성/종료
  - 요청을 워커에 분배
  - 워커가 죽으면 자동 재시작
  - 시그널 처리 (SIGTERM, SIGHUP 등)

### 워커 프로세스 (Worker Process)

- **역할**: 실제 HTTP 요청을 처리
- **책임**:
  - WSGI 애플리케이션 호출
  - 요청/응답 처리
  - 마스터와 통신

### 프로세스 확인 실습

Gunicorn을 실행한 상태에서 다른 터미널에서:

```bash
ps aux | grep gunicorn
```

출력 예시:

```
user  12345  0.1  0.5  마스터 프로세스
user  12346  0.2  0.8  워커 프로세스 1
user  12347  0.2  0.8  워커 프로세스 2
user  12348  0.2  0.8  워커 프로세스 3
user  12349  0.2  0.8  워커 프로세스 4
```

워커 수는 `--workers` 옵션으로 지정한 수만큼 생성됩니다.

## 4.2 워커 타입

Gunicorn은 여러 워커 타입을 지원합니다.

### sync (기본값)

- **특징**: 동기 방식, 한 번에 하나의 요청 처리
- **사용 시나리오**: CPU 집약적 작업, 간단한 애플리케이션
- **장점**: 안정적, 디버깅 쉬움
- **단점**: 동시성 낮음

```bash
gunicorn app:application --worker-class sync --workers 4
```

### gevent

- **특징**: 비동기 I/O, 코루틴 기반
- **사용 시나리오**: I/O 집약적 작업 (DB 쿼리, 외부 API 호출)
- **장점**: 높은 동시성, 적은 메모리 사용
- **단점**: CPU 집약적 작업에는 부적합

```bash
pip install gevent
gunicorn app:application --worker-class gevent --workers 4
```

#### 비동기 I/O란?

**동기 I/O (Synchronous I/O)**와 **비동기 I/O (Asynchronous I/O)**의 차이를 이해하는 것이 중요합니다.

**동기 I/O의 동작 방식**:

```
요청 1: DB 쿼리 시작 → 대기 → 결과 수신 → 다음 작업
요청 2: (요청 1이 완료될 때까지 대기)
요청 3: (요청 1이 완료될 때까지 대기)
```

동기 방식에서는 I/O 작업(DB 쿼리, 파일 읽기, 네트워크 요청 등)이 완료될 때까지 **프로세스가 블로킹**되어 다른 작업을 할 수 없습니다.

**비동기 I/O의 동작 방식**:

```
요청 1: DB 쿼리 시작 → 다른 작업으로 전환
요청 2: 외부 API 호출 시작 → 다른 작업으로 전환
요청 3: 파일 읽기 시작 → 다른 작업으로 전환
...
(모든 I/O 작업이 완료되면 각각 처리)
```

비동기 방식에서는 I/O 작업을 시작한 후, **작업이 완료되기를 기다리지 않고** 다른 작업을 수행할 수 있습니다. I/O 작업이 완료되면 콜백이나 코루틴을 통해 결과를 처리합니다.

**"동기라면서 왜 비동기 IO??"라는 질문에 대한 답변**:

- **동기(Synchronous)**: 코드 실행 순서가 순차적이라는 의미입니다. 한 줄씩 실행됩니다.
- **비동기 I/O(Asynchronous I/O)**: I/O 작업만 비동기로 처리한다는 의미입니다.

즉, 코드 자체는 동기적으로 작성되지만, I/O 작업(DB 쿼리, 네트워크 요청 등)만 비동기로 처리하여 **대기 시간 동안 다른 작업을 수행**할 수 있습니다.

**gevent에서의 비동기 I/O 활용**:

gevent는 Python의 표준 라이브러리 함수들(`socket`, `urllib`, `time.sleep` 등)을 자동으로 비동기 I/O로 변환합니다. 이를 통해 하나의 워커 프로세스가 수백, 수천 개의 동시 요청을 처리할 수 있습니다.

예시:

- 4개의 sync 워커: 동시에 4개 요청 처리
- 4개의 gevent 워커: 동시에 수백~수천 개 요청 처리 가능 (I/O 대기 시간 활용)

#### 코루틴이란?

**코루틴(Coroutine)**은 함수 실행을 일시 중지하고 나중에 재개할 수 있는 함수입니다.

**스레드와의 차이점**:

| 스레드 (Thread)            | 코루틴 (Coroutine)             |
| -------------------------- | ------------------------------ |
| OS 레벨에서 관리           | 애플리케이션 레벨에서 관리     |
| 컨텍스트 스위칭 비용 큼    | 컨텍스트 스위칭 비용 매우 작음 |
| 메모리 사용량 큼 (MB 단위) | 메모리 사용량 작음 (KB 단위)   |
| 수백 개 생성 시 부담       | 수만 개 생성 가능              |

**코루틴의 동작 원리**:

```python
# 개념적 예시 (gevent 내부 동작)
def handle_request():
    # I/O 작업 시작
    data = db.query()  # 여기서 코루틴 일시 중지
    # 다른 코루틴이 실행됨
    # I/O 완료 시 이 지점부터 재개
    return process(data)
```

I/O 작업이 시작되면 코루틴이 일시 중지되고, 다른 코루틴이 실행됩니다. I/O가 완료되면 원래 코루틴이 재개됩니다.

**gevent에서의 코루틴 활용**:

gevent는 각 요청을 코루틴으로 처리합니다. 하나의 워커 프로세스 내에서 수천 개의 코루틴이 동시에 실행될 수 있으며, I/O 대기 중인 코루틴은 자동으로 일시 중지되고 다른 코루틴이 실행됩니다.

이를 통해 **프로세스 수는 적게 유지하면서도 높은 동시성**을 달성할 수 있습니다.

### gthread

- **특징**: 스레드 기반
- **사용 시나리오**: I/O 집약적 작업, C 확장 모듈 사용 시
- **장점**: 스레드 안전한 라이브러리와 호환
- **단점**: GIL(Global Interpreter Lock) 제약

```bash
gunicorn app:application --worker-class gthread --threads 4 --workers 2
```

### Spring/Tomcat과의 비교

| Spring/Tomcat           | Gunicorn                               |
| ----------------------- | -------------------------------------- |
| 스레드 풀 (Thread Pool) | 워커 프로세스 풀 (Worker Process Pool) |
| `maxThreads` 설정       | `--workers` 설정                       |
| 스레드당 하나의 요청    | 프로세스당 하나의 요청 (sync)          |
| 공유 메모리             | 프로세스 간 메모리 분리                |

**핵심 차이**: Tomcat은 스레드를 사용하고, Gunicorn은 프로세스를 사용합니다. 프로세스는 메모리를 공유하지 않으므로 더 안정적이지만, 메모리 사용량이 더 큽니다.

## 4.3 워커 수 결정

### 권장 공식

```
워커 수 = (2 × CPU 코어 수) + 1
```

예: 4코어 CPU → `(2 × 4) + 1 = 9` 워커

### 실습: 워커 수에 따른 동시성 테스트

`gunicorn/codes/02_worker_demo/app.py`:

```python
import time
import os

def application(environ, start_response):
    """워커 동작 확인용 애플리케이션"""
    status = '200 OK'
    headers = [('Content-Type', 'text/plain; charset=utf-8')]
    start_response(status, headers)

    # 프로세스 ID와 작업 시뮬레이션
    pid = os.getpid()
    time.sleep(1)  # 1초 대기 (동시성 테스트용)

    return [f'Worker PID: {pid}\n'.encode('utf-8')]
```

실행:

```bash
gunicorn app:application --workers 4
```

여러 터미널에서 동시에 요청:

```bash
# 터미널 1
curl http://127.0.0.1:8000

# 터미널 2
curl http://127.0.0.1:8000

# 터미널 3
curl http://127.0.0.1:8000

# 터미널 4
curl http://127.0.0.1:8000
```

각 요청이 다른 PID를 반환하면 워커가 제대로 분산되고 있음을 확인할 수 있습니다.
